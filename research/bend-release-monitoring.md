# Monitoring Bend releases for plugin compatibility

Researched 2026-09-27 against the [Bend 2 repository](https://github.com/bendlang/bend), its public GitHub API, [installer](https://bend-lang.com/install.sh), and GitHub's event/API documentation. This describes the public release channel; the private steps used by Bend maintainers to produce releases are not established here.

## What is released

- **Source of truth:** Bend 2 moved from `HigherOrderCO/Bend2` to [`bendlang/bend`](https://github.com/HigherOrderCO/Bend2). The [Bend 2 README](https://github.com/bendlang/bend/blob/main/README.md) directs users to `https://bend-lang.com/install.sh`. The older [`HigherOrderCO/Bend`](https://github.com/HigherOrderCO/Bend) and its `cargo install bend-lang` instructions describe Bend 1, so crates.io is not a suitable Bend 2 release signal.
- **Observed tag and asset pattern:** The [published releases](https://api.github.com/repos/bendlang/bend/releases?per_page=100) and [repository tags](https://api.github.com/repos/bendlang/bend/tags?per_page=100) both currently list 25 matching versions, `v2.0.8` through `v2.0.32`. Release names are `Bend 2.0.N`; each observed release is non-draft, non-prerelease, and has four archives named `bend-2.0.N-{linux,darwin}-{x64,arm64}.tar.gz`. This is an observed convention, not a guarantee for future versions. The current [latest release](https://api.github.com/repos/bendlang/bend/releases/latest) is `v2.0.32`, published 2026-09-27 15:41 UTC. Releases can arrive more than once per day: `v2.0.30`, `.31`, and `.32` all published on September 27 ([release list](https://api.github.com/repos/bendlang/bend/releases?per_page=10)).
- **Install options:** The [installer](https://bend-lang.com/install.sh) currently hardcodes version `2.0.32`, downloads the platform archive from `github.com/bendlang/bend/releases/download/v2.0.32/…`, verifies SHA-256, and installs `bin/bend`, `bend2/`, and `guide/` under `BEND_HOME` (default `~/.bend`). It supports Linux/macOS on x64/arm64, and documents WSL for Windows. The [release notes](https://github.com/bendlang/bend/releases/tag/v2.0.32) also offer Homebrew (`brew install bendlang/bend/bend`) and Nix (`nix profile install github:bendlang/bend`). For CI, a release asset or tag is safer to select explicitly than a mutable installer/Homebrew/Nix latest alias. The [release API](https://api.github.com/repos/bendlang/bend/releases/tags/v2.0.32) exposes each asset's URL and `sha256:` digest, and the release notes publish the checksums too.
- **Public release mechanics:** The installer says `release.ts` generates it with the version and archive checksums. The [public repository `.github` directory](https://api.github.com/repos/bendlang/bend/contents/.github) currently has issue templates but no public Actions release workflow. Thus the available evidence shows where releases are published and how they are installed, but not whether the maintainer's publishing steps are automated.

## Detection and trigger choices

| Option | Feasibility for this repository |
| --- | --- |
| Poll [`GET /repos/bendlang/bend/releases`](https://docs.github.com/en/rest/releases/releases#list-releases) from a [scheduled workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) | **Recommended.** Public releases can be read without upstream permission. Filter published stable releases, require a matching Linux asset/digest, and process every unseen release ID/tag in order. Paginate if needed. A latest-only poll can miss intermediate releases when several publish between runs. GitHub says scheduled jobs may be delayed or dropped, and public-repo schedules disable after 60 days without activity; retain a durable processed-release cursor and reconcile the list on the next run. A six-hour schedule away from the top of the hour, plus `workflow_dispatch` for manual retry, is a reasonable starting point. Public API reads work without authentication, subject to [60 requests/hour/IP](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api); a token can raise the limit. |
| Poll [`GET /repos/bendlang/bend/releases/latest`](https://docs.github.com/en/rest/releases/releases#get-the-latest-release) | Simple for a *latest-version smoke test*, but it intentionally returns only the most recent non-draft, non-prerelease release, and can skip intervening versions. GitHub sorts its selection by release `created_at`, not publication time. |
| Poll [tags](https://docs.github.com/en/rest/repos/repos#list-repository-tags) | Useful for detecting source tags, but a tag alone does not prove that a release and tested archive assets have been published. Prefer the release list for a runnable candidate. GitHub documents that release-list responses omit tags without associated releases. |
| Upstream `release.published` webhook → [`repository_dispatch`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#repository_dispatch) here | Near-immediate, but needs an upstream webhook/GitHub App installation and a relay with write permission to dispatch this repository. `on: release` in *our* workflow only receives releases of *our* repository. GitHub requires upstream repository admin/owner access to create its webhook ([webhook types](https://docs.github.com/en/webhooks/types-of-webhooks#repository-webhooks)); the [dispatch endpoint](https://docs.github.com/en/rest/repos/repos#create-a-repository-dispatch-event) needs Contents write access here. This is unnecessary infrastructure for a first implementation. |

## Fit with this repository

The existing [verification workflow](../.github/workflows/verify.yml) checks out a full Bend commit from [`ci/bend-test-toolchain.properties`](../ci/bend-test-toolchain.properties), verifies that commit and Bun revision, then runs `./gradlew check` and plugin packaging. Its pinned compiler checks, build configuration, and semantic helper provenance are intentional. A release monitor should therefore run a **separate candidate compatibility job** against a specific published tag/commit and asset, with a deliberate temporary pin override or a dedicated candidate test path. Keep the existing pinned push/PR gate stable; do not silently replace its compiler with `latest`. Record the candidate tag, resolved commit, asset digest, Bun revision, and test result, then explicitly promote a compatible compiler pin through review. This last design is a recommendation inferred from the repository's current pin checks, not an upstream Bend requirement.

In particular, the existing Gradle `test` task depends on [`verifyBendTestInputs`](../build.gradle.kts), and both that script and [`RealBendCompilerFixture`](../src/test/scala/com/dearlordylord/bend/idea/adapters/cli/RealBendCompilerFixture.scala) reject a checkout that differs from the recorded commit. The [structured helper](../src/main/resources/semantic/bend-structured-helper.ts) also checks hashes of three Bend 2.0.25 source files and returns no optional operations for other sources. Pointing today's full suite at a new tag would therefore produce pin failures, and simply bypassing the pin would not establish structured-helper compatibility.

### Suggested first implementation

1. Schedule a release-list reconciliation and allow manual dispatch. Persist successfully tested release IDs/tags in a dedicated state branch or equivalent durable store. Serialize monitor runs; queue every unseen stable published release with a Linux x64 asset and digest, including releases published between polls. Record failures separately and leave them eligible for retry.
2. For each candidate, download and verify the **published archive**, then run a focused real-compiler compatibility task against its `bin/bend` and matching `bend2/base.bend`. Make absent inputs and skipped tests fail that task. Cover a complete check, unfinished hole, ordinary diagnostic, and any compiler-facing editor action whose behavior is expected to work across Bend versions. Keep the pinned `./gradlew check` as the separate regression gate.
3. Publish the tag, immutable release/commit identifiers, asset digest, and test report as a CI artifact or issue comment. A failure should be visible to maintainers; passing should not automatically change the supported compiler pin. Review new compiler behavior and the helper's source-level compatibility before updating the pin and README.

## Implemented follow-up

The [release compatibility workflow](../.github/workflows/bend-releases.yml) now polls every six hours and accepts a manual tag for retry. [`ci/bend_release_monitor.py`](../ci/bend_release_monitor.py) processes published releases after the Bend 2.0.25 pin in publication order, up to 20 per run, verifies each archive digest, and records both passing and failing results on a dedicated `bend-release-results` branch. A changed archive digest is tested again. The [release editor fixture](../src/test/scala/com/dearlordylord/bend/idea/features/checking/BendReleaseEditorSmokeTest.scala) exercises Check Current Bend File with the archive's compiler and Base. The ordinary pinned suite and the source-hash-limited structured helper remain separate. This provides eventual detection after a release; GitHub schedules can be delayed, and it is not an upstream release webhook.
