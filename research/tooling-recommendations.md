# Tooling recommendations for Bend IDEA

Assessed 2026-09-23 against [the Scala ecosystem survey](scala-ecosystem-and-agentic-guidance.md), the current repository, and the first-party sources linked below. This is advice for the existing Scala 3 IntelliJ plugin, not a dependency change or a claim that a proposed tool has been integrated. Mechanical refactoring cost is acceptable; the deciding factor is whether a tool improves the correctness and maintainability of Bend source editing and compiler-backed analysis.

## Recommendation

Keep Gradle and the IntelliJ Platform Plugin as the product build. Keep the core source, graph, and analysis policies as Scala 3 data and functions, with IntelliJ and subprocess effects at their existing adapter boundaries. Spend the next tooling effort on reproducible real-compiler evidence, a clearer check-state transition model, consistent formatting and compiler diagnostics, and a focused Scala 3.9 LTS evaluation. Trial Metals MCP as an agent's semantic navigation aid after confirming it imports this build. No application effect runtime or agent orchestration framework currently addresses a demonstrated quality gap.

This follows the distinction in [ARCHITECTURE.md](../ARCHITECTURE.md): editable source, root-relative loaded graphs, and compiler judgments have different authorities and lifetimes. A tool is valuable here when it helps preserve those boundaries, not merely when it offers a more functional programming style.

## Evidence from the current code

- [`build.gradle.kts`](../build.gradle.kts) uses Gradle's Scala plugin and JetBrains' IntelliJ Platform Gradle Plugin, pins JDK 21, runs editor tests and `architectureTest` through `check`, and configures packaging and compatibility verification. Scala 3.3.7 is selected in [`gradle.properties`](../gradle.properties). Compiler options are currently `-feature` and `-Werror`; there is no repository formatting or lint configuration.
- [`BendCheckResult`](../src/main/scala/com/dearlordylord/bend/idea/analysis/model/BendCheckResult.scala) represents outcome, completeness, unsafe or foreign reliance, freshness, root identity, checked sources, and source mappings separately. [`BendPublicationPolicy`](../src/main/scala/com/dearlordylord/bend/idea/analysis/checking/BendPublicationPolicy.scala) is an immutable publication predicate. These are good foundations for domain-specific state modeling without a general effect system.
- [`BendCheckSession`](../src/main/scala/com/dearlordylord/bend/idea/adapters/intellij/BendCheckSession.scala) and [`BendBackgroundChecking`](../src/main/scala/com/dearlordylord/bend/idea/adapters/intellij/BendBackgroundChecking.scala) own generations, results by root, document and VFS listeners, debounce, retries, cancellation, read actions, and disposal. [`BendBoundedProcess`](../src/main/scala/com/dearlordylord/bend/idea/adapters/process/BendBoundedProcess.scala) owns bounded process execution and termination. These are the areas where concurrency mistakes would matter; a replacement runtime would still have to obey IntelliJ's threading and lifecycle rules.
- [`BendGraphLoader`](../src/main/scala/com/dearlordylord/bend/idea/workspace/loading/BendGraphLoader.scala) owns ordered import traversal and namespace conflicts. [`BendCliCheckBackend`](../src/main/scala/com/dearlordylord/bend/idea/adapters/cli/BendCliCheckBackend.scala) probes `--check-only`, materializes snapshots, and limits external execution. Editor fixtures and real Bend subprocess tests already exercise behavior across these boundaries. [`ArchitectureRules`](../src/test/scala/com/dearlordylord/bend/idea/architecture/ArchitectureRules.scala) enforces compiled package dependencies. Preserve these complementary forms of evidence.
- The [real-compiler tests](../src/test/scala/com/dearlordylord/bend/idea/adapters/cli/BendCliGraphCheckTest.scala) point at `.references/bend/bend2/main.ts` and launch it with `npx --yes bun`. `.references/` is ignored by [`.gitignore`](../.gitignore) and has no tracked files. The [CI workflow](../.github/workflows/verify.yml) checks out this repository and installs JDK 21, but does not visibly provision that Bend checkout or pin Bun. **Inference from the checked-in configuration:** a fresh CI runner cannot establish the intended real-compiler gate as written. This is a high-priority reproducibility issue under A6–A7, not a claim based on running CI.

## Ranked choices

| Priority | Choice | Concrete action and reason |
|---|---|---|
| 1 | Reproducible Bend integration gate | Provision the exact approved Bend revision and a pinned Bun executable in CI; make the test harness call that executable directly. Check the compiler and Base identities before the tests run. Keep the protected local reference checkout untouched. This makes A6's check-only/offline evidence and A7's compiler judgments meaningful on a fresh runner. |
| 2 | Pure checking transitions | Extract the generation, invalidation, cancellation-request, publication, and eviction decisions from the IntelliJ services into a small immutable transition function in the analysis owner. Leave listeners, locks, read actions, workers, and disposal in the IntelliJ adapter. Exercise event sequences such as edit-during-check, dependency creation, compiler replacement, manual preemption, and disposal. This directly strengthens A5 without adding a second runtime. |
| 3 | Pinned Scalafmt and compiler warnings | Add `.scalafmt.conf` with a pinned version and Scala 3 dialect, plus a Gradle formatting check in CI. Evaluate relevant Scala compiler warning categories one at a time with `-Werror`, since `-Werror` only promotes warnings that are emitted. Avoid a blanket lint rule that obscures deliberate IntelliJ interop or source-recovery code. |
| 4 | Scala 3.9 LTS evaluation | Try the new LTS in a focused change. Compile, run editor fixtures and real compiler tests, build the plugin, run the Plugin Verifier, and inspect the packaged Scala runtime and extension instantiation. The project already requires JDK 21, so the newer Scala line's JDK 17 floor is compatible. Treat migration diagnostics and runtime packaging as evidence, not as reasons to postpone the evaluation indefinitely. |
| 5 | Metals MCP trial | Confirm that Metals imports this particular Gradle build and resolves project symbols and IntelliJ dependencies accurately. If it does, use its symbol, usage, source, and documentation queries to aid agents during refactors. Keep Gradle's `check`, `buildPlugin`, and `verifyPlugin` as the authoritative product checks. |

### The compiler test gate comes first

The test suite's domain strength is its use of a real pinned Bend compiler for judgments such as no execution of `main`, offline dependency loading, and snapshot mapping. An agent or static linter cannot replace that evidence. The suite should receive a known compiler runtime and source revision through an explicit fixture contract. Running `npx --yes bun` inside individual tests can resolve tooling at test time, while the ignored `.references` path depends on local state. A fresh-runner setup should fail clearly when the approved compiler inputs are absent, and should never silently switch to a different compiler.

The existing Gradle/JetBrains tasks remain the appropriate gate for packaging and platform compatibility. The [JetBrains plugin development documentation](https://plugins.jetbrains.com/docs/intellij/developing-plugins.html) describes that build integration. If CI needs a separately provisioned compiler checkout, keep its exact revision and acquisition method visible in the workflow or a dedicated setup script. Respect the repository rule that the supplied reference checkouts and trusted Bend core are protected.

### Model state before adopting a runtime

`BendPublicationPolicy.mayPublish` already answers one important question from immutable facts. A modest next step is a transition such as `transition(rootState, event) -> (newState, requestedEffects)`. Events can include source or dependency changes, start requests, worker completion, configuration changes, and disposal. The adapter then performs requested cancellation, capture, daemon refresh, or process execution. This is a refactor within A4–A5's current boundary; it need not create a generic effect interpreter.

Keep the existing observable tests. Add focused lower-level tests only where they explore a concrete risk that the editor or process fixture does not explain well: generation ordering, root-owned diagnostics, graph cycles/namespace conflicts, or UTF-16 offset composition. Property-based generation is a reasonable option for offset mappings and graph shapes if examples leave meaningful edge cases uncovered. It should supplement, not replace, IntelliJ editor fixtures or the real compiler.

The [IntelliJ threading model](https://plugins.jetbrains.com/docs/intellij/threading-model.html), [background process guidance](https://plugins.jetbrains.com/docs/intellij/background-processes.html), and [execution contexts](https://plugins.jetbrains.com/docs/intellij/execution-contexts.html) should guide any later worker refactor. JetBrains recommends its coroutine execution context for new plugins targeting this platform era; Scala integration needs a deliberate bridge if adopted. The key correctness properties remain short read actions, timely invalidation, project disposal, process termination, and rejection of obsolete results.

### Scala toolchain and code quality

Scalafmt is a good immediate fit: it standardizes Scala 3 layout for human and agent edits without changing runtime architecture. Its [installation guide](https://scalameta.org/scalafmt/docs/installation.html) documents IntelliJ support and Gradle integrations through external plugins; its [configuration guide](https://scalameta.org/scalafmt/docs/configuration.html) requires an explicit version and dialect. Choose one Gradle integration, pin the formatter, and check formatting in CI. A large first formatting change can be isolated so later semantic diffs remain readable.

The [Scala 3.9 LTS announcement](https://scala-lang.org/news/3.9/) recommends 3.9 as the new conservative baseline and explains the 3.3-to-3.9 compatibility boundary. This plugin is not a published Scala library, so source and bundled-runtime compatibility are more relevant than downstream Scala artifact compatibility. Still, its IntelliJ extension classes and package require full build and verifier evidence. Upgrade the compiler and runtime together; do not infer plugin compatibility from compilation alone.

Scalafix is a later, narrower option. Its [documentation](https://scalacenter.github.io/scalafix/docs/users/installation.html) supports Scala 3.9 and explains SemanticDB requirements for semantic rules, but its common build integration is sbt rather than this Gradle plugin build. Adopt it only for a specific recurring refactor or enforceable rule, after proving its Gradle/Scala setup works. ArchUnit already checks the architecture's dependency direction; keep that existing domain-specific gate.

### Agent tooling

The [Metals MCP tool list](https://scalameta.org/metals/docs/features/mcp/) includes symbol inspection, usages, source lookup, module compilation, tests, formatting, and Scalafix operations. [Metals lists Gradle support](https://scalameta.org/metals/docs/build-tools/overview/), but this build also contains IntelliJ platform fixtures, signing, and compatibility verification. A trial should show correct import and useful symbol answers on `BendCheckSession`, `BendGraphLoader`, and the Scala IntelliJ API before making it a standard agent workflow. Metals can provide semantic evidence; Gradle remains the build authority.

The existing `AGENTS.md`, `ARCHITECTURE.md`, and `REVIEWER.md` already define the repository workflow and review contract. A focused skill may eventually help repeat a specialized IntelliJ fixture or Bend snapshot procedure. Orca, Scala Semantic Harness, Kyo's AI modules, and a new repository-wide agent framework would add orchestration without addressing the concrete compiler-test or platform-lifecycle gaps identified above. The [ecosystem survey](scala-ecosystem-and-agentic-guidance.md) has the project links and maturity notes for those options.

## Runtime library decision

Use Scala 3 enums, case classes, immutable collections, `Option`, and `Either` for the current shared policies. Add Cats Core if a real consumer needs a particular abstraction such as validated error accumulation or ecosystem interoperability. Do not add it simply to make the code appear more functional.

Cats Effect, ZIO, Ox, and Kyo offer different concurrency and effect models. The current plugin already has a platform owner for project lifetime and OS processes. A new runtime would require an explicit mapping for IntelliJ read/write actions, cancellation, disposal, and subprocess cleanup, as well as new packaging and verifier evidence. If future orchestration becomes complex enough to justify one, prototype exactly one option inside an adapter and measure those integration points before changing the product architecture. The survey's library comparison remains a useful reference; no current source evidence calls for a wholesale runtime migration.

## Suggested order of work and acceptance evidence

1. Repair the fresh-runner compiler fixture. Demonstrate that `./gradlew check` on a provisioned JDK 21 runner executes the intended editor and real Bend tests and that the compiler revision/runtime are fixed.
2. Add the pure transition model only around the current check scheduling/publication complexity. Show focused race tests and retain editor fixtures for observable behavior. Extend compiled architecture checks if a new package boundary is introduced.
3. Pin Scalafmt and add its check to CI. Add warning categories incrementally, resolving real findings rather than suppressing broad areas.
4. Evaluate Scala 3.9 with `check`, `buildPlugin`, and `verifyPlugin`, plus inspection of the installed plugin's extension loading. Record any source migration and packaging changes.
5. Trial Metals MCP on a disposable local setup. Keep it only if it imports this project and supplies reliable semantic answers that plain code search and Gradle output do not.

This document is a source-and-documentation assessment. No build, test, CI run, Metals import, or Scala 3.9 migration was performed for it.
