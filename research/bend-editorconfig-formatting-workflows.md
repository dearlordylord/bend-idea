# Bend formatting, EditorConfig, and commit checks

Assessed 2026-09-28. This note addresses a user's possible request for automatic Bend formatting and a pre-commit lint gate. It is research, not an implemented behavior or an issue acceptance criterion.

## What each mechanism does

| Mechanism | What it can provide | What it does not provide by itself |
|---|---|---|
| `.editorconfig` | Per-file values such as `indent_style`, `indent_size`, `tab_width`, line endings, final newline, and trailing whitespace. IntelliJ overlays these on its code-style scheme. | A parser/formatter for Bend, a command-line lint check, or an automatic save/commit trigger. [EditorConfig specification](https://spec.editorconfig.org/); [JetBrains EditorConfig help](https://www.jetbrains.com/help/idea/editorconfig.html). |
| IntelliJ Bend formatter | `Code > Reformat Code`, plus IDE Actions on Save or Commit Checks if enabled by the user. | A repository-wide hook usable by other editors or CI. [Formatter SDK](https://plugins.jetbrains.com/docs/intellij/code-formatting.html); [reformat help](https://www.jetbrains.com/help/idea/reformat-and-rearrange-code.html). |
| Bend `--check-only` | Checks a root and its imports without running `main`. | Style or formatting enforcement. [Pinned Bend CLI](https://github.com/bendlang/bend/blob/ff7a40cc9070a34c78399ecd2bbe46a044ad9b4b/bend2/main.ts#L175-L225). |
| Git pre-commit hook | Can reject a commit when a chosen command exits nonzero. | A formatter or reliable team-wide policy; Git permits `--no-verify`, so CI must repeat a required check. [Git hooks](https://git-scm.com/docs/githooks); [Git FAQ](https://git-scm.com/docs/gitfaq). |

The user phrase “precommit hook to lint all the bend code” is ambiguous. It may mean compiler validity, style/format conformance, or both. For an interactive workflow, likely desired behavior is *format on save* and perhaps *format before commit*; for a shared gate, use an idempotent formatter in check mode plus a separate `--check-only` command for compiler judgments. This is an inference, not a claim about the user's exact intent.

## Existing Bend formatter changes the options

The pinned upstream Bend checkout includes `tools/bend-fmt-lsp`, an official **formatting-only** language server. Its README says it supports full-document formatting, preserves comments, literals, line endings and final-newline state, and returns no edit when it cannot safely tokenize. It has no diagnostics, range formatting, or on-type formatting. It requires Node.js 22 or newer. [Pinned README](https://github.com/bendlang/bend/blob/ff7a40cc9070a34c78399ecd2bbe46a044ad9b4b/tools/bend-fmt-lsp/README.md).

The server passes the LSP `textDocument/formatting` request's `tabSize` and `insertSpaces` to `formatBend`; it does not read `.editorconfig`. Its output uses that `tabSize` as the indentation step for spaces, or one tab per depth for tabs. However, it interprets **existing** tabs as eight columns when reconstructing indentation depth, independent of the requested tab size. That is a concrete `tab_width` compatibility risk. It also implements only full-document replacement edits and exposes no formatter/check CLI in the inspected package. [Pinned server](https://github.com/bendlang/bend/blob/ff7a40cc9070a34c78399ecd2bbe46a044ad9b4b/tools/bend-fmt-lsp/src/server.ts); [pinned formatter](https://github.com/bendlang/bend/blob/ff7a40cc9070a34c78399ecd2bbe46a044ad9b4b/tools/bend-fmt-lsp/src/formatter.ts#L160-L209); [package scripts](https://github.com/bendlang/bend/blob/ff7a40cc9070a34c78399ecd2bbe46a044ad9b4b/tools/bend-fmt-lsp/package.json).

The EditorConfig specification distinguishes indentation **columns per level** (`indent_size`) from displayed tab width (`tab_width`), and permits mixed tabs and spaces when needed. LSP's `tabSize`/`insertSpaces` pair cannot represent every EditorConfig combination without an explicit mapping or formatter extension. [EditorConfig specification](https://spec.editorconfig.org/).

## Other language workflows and the platform boundary

- JetBrains' custom-language formatter contract provides `FormattingContext.codeStyleSettings`; a `FileTypeIndentOptionsProvider` sets defaults while allowing tab and indent configuration. Formatting blocks control whitespace edits. The SDK also offers an `AsyncDocumentFormattingService` extension for an external formatter. Thus the platform and the repository's package graph do **not** prohibit EditorConfig-aware Bend formatting; the formatter must consume the effective settings and preserve Bend syntax. [JetBrains formatter SDK](https://plugins.jetbrains.com/docs/intellij/code-formatting.html).
- Go support illustrates a dual path: the IDE formatter handles incomplete code and selected blocks; `gofmt` may run on Reformat Code and on save. This suggests preserving the plugin's conservative editing behavior while evaluating a full-document upstream formatter. [JetBrains Go tools](https://www.jetbrains.com/help/idea/integration-with-go-tools.html).
- PyCharm documents `.editorconfig`-driven reformatting, Actions on Save, and Commit Checks, which are user-configured IDE triggers. They are distinct from a Git hook invoked by any Git client. [PyCharm reformat help](https://www.jetbrains.com/help/pycharm/reformat-and-rearrange-code.html); [Git hooks](https://git-scm.com/docs/githooks).
- Rustfmt illustrates an independent command-line formatter with its own `rustfmt.toml` configuration and a `cargo fmt --check` CI check. A language formatter's own configuration may differ from EditorConfig; one needs an intentional mapping if IDE and CLI output must match. [Rustfmt configuration](https://rust-lang.github.io/rustfmt/); [Rust Reference CI guide](https://rust-lang.github.io/reference/dev-guide/tests.html).

JetBrains also provides a command-line IDE formatter, which loads file-type plugins and parent `.editorconfig` files. Its documented `-d`/`-dry` mode exits nonzero when formatting would change a file, so it is an immediate *possible* style-check command without building a new CLI. It launches an IDE instance and cannot run while another instance is running, making it awkward as a frequent developer pre-commit hook (and it still inherits the current Bend formatter's limited behavior). Validate the option against the repository's pinned IDE before relying on it in CI. [JetBrains command-line formatter](https://www.jetbrains.com/help/idea/command-line-formatter.html).

## Implications for this repository

The current [Bend formatter](../src/main/scala/com/dearlordylord/bend/idea/features/formatting/BendFormattingModelBuilder.scala) hard-codes a two-space body indent for its narrow eligible case and leaves most line breaks read-only. The [indent provider](../src/main/scala/com/dearlordylord/bend/idea/features/editing/BendIndentOptionsProvider.scala) supplies two-space defaults, but the formatter does not use the effective indent options. [Enter](../src/main/scala/com/dearlordylord/bend/idea/features/editing/BendEnterHandler.scala) and [Backspace](../src/main/scala/com/dearlordylord/bend/idea/features/editing/BendBackspaceHandler.scala) have separate indentation paths. These are implementation gaps, not architectural prohibitions. A common policy should map effective indent size, tab use, and tab width to whitespace generation and indentation measurement, with editor fixtures for `.editorconfig` overrides.

The plugin is Scala 3 and its `features.formatting` package owns formatting. Pure source/indentation policy can be shared where needed; IntelliJ handles and write commands stay in the platform/feature boundary. An external formatter would need a process adapter, bounded lifecycle, cancellation, and stale-document protection, rather than using the compiler-check backend as an arbitrary command runner. That follows [ARCHITECTURE.md](../ARCHITECTURE.md) dependency rules and A4–A7's source, effect, and freshness contracts. Full-document edits need stronger evidence than punctuation-only edits: preservation of strings/comments, imports, proof syntax, incomplete buffers, caret/undo behavior, and consistency with compiler results.

No tracked `.bend` files or repository formatting hook are present here. This plugin repository is different from a user's Bend source repository. A local hook in this repo would mainly exercise fixtures; it would not install itself into users' projects. [Git hooks](https://git-scm.com/docs/githooks); [pre-commit staged-file behavior and `--all-files`](https://pre-commit.com/).

## Recommended decision sequence

1. Clarify the requested outcome as three separate user-visible options: EditorConfig-aware editing/reformatting, optional IDE format-on-save/commit, and a reproducible CLI format check for a Bend project. The first two are plugin behavior; the third must be a tool or script runnable outside IntelliJ.
2. Fix effective indent settings in the current plugin first, with editor fixtures for `indent_size = 4`, `indent_style = tab`, `tab_width`, nested `.editorconfig`, and incomplete Bend source. This is a narrow conforming change under `features.editing`/`features.formatting`.
3. For an interim check, evaluate IntelliJ's documented `format -d` command with this plugin installed. It can read `.editorconfig` but requires an IDE installation, cannot run alongside an open instance, and currently checks only the conservative edits the plugin knows how to make. For a lightweight cross-editor hook, evaluate the pinned upstream formatter as the potential canonical *whole-file* formatter. It needs a deterministic CLI/check wrapper or upstream CLI support, pinned Node and Bend revision, EditorConfig mapping (including differing `indent_size`/`tab_width`), and a tab-depth fix before promising identical IDE and hook output. Compare its edits and compiler verdicts on real Bend fixtures. Do not silently replace the current conservative formatter for incomplete buffers.
4. If style enforcement is required across contributors, run the same pinned check in CI. A pre-commit hook can provide faster local feedback; normally it checks staged `.bend` files, while `pre-commit run --all-files` is an explicit repository sweep. Keep compiler `--check-only` separate because it answers a different question.

No plugin code, Bend tool, IDE fixture, hook, or CI check was run for this research note.
